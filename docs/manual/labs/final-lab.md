# Final Lab：综合验收与答辩

> **对应教材**：[第 11 章：综合验收](../book/ch11-comprehensive-assessment.md)

> **本 Lab 概览**
>
> - **学完能做什么**：把十个 Lab 的成果整合为一份可追溯的最终交付：报告、Spec 与实现、验证证据、答辩材料，并完成课程公布的实验验收与人工审查。
> - **预计耗时**：8–12 小时，建议安排 1 周。报告与证据整理约占一半，长时间运行、演示准备与答辩演练占另一半。
> - **前置依赖**：已完成 Lab 1–10，并保留实验要求的可复现构建、测试、QEMU/硬件与人工复核证据。
> - **产出物**：最终报告、全部 Spec 与源码、验证证据包、可复现归档、答辩材料。
> - **评分构成**：质量门禁 70% + 设计理据 20% + 挑战/加分 10%（可选）。实际分值以教师公布为准；答辩表现计入人工审查部分。
> - **实际耗时**：在提交物里记录本次 Lab 实际投入小时数。

Final Lab 不是重复执行一遍命令。它审查从设计、实现、验证到演示的完整追溯链，并要求学生解释失败与取舍。

## 1. 最终学生主链

```text
设计与范围确认 → Spec 与接口 → 使用选定 Coding Agent 实现
→ 项目测试/build → QEMU/硬件 → 报告与答辩
```

这条链的每一环都要能在答辩时讲清楚：为什么这么设计、证据在哪、失败如何定位。

## 2. 提交物

### 2.1 最终报告

报告至少包含：系统目标与 non-goals、架构图、各模块职责、关键 ABI、1～3 条组合不变量、个性化目标结果、硬件状态、已知限制和复现步骤。报告必须区分自动验证、QEMU 运行、真实硬件运行与人工验收。

推荐正文结构：

1. 系统目标、范围与可运行演示；
2. 从启动到用户空间的架构与数据流；
3. 内存、中断、进程、文件系统和资源模型；
4. 关键 ABI 与跨模块不变量；
5. 个性化目标的基线、方法、结果和负面取舍；
6. QEMU 与硬件证据边界；
7. 失败案例、已知限制和下一步。

### 2.2 Spec 与实现

- 唯一 DesignSpec；
- 每个实现模块的 L1/L2/L3 ModuleSpec；
- syscall、IPC、驱动或用户/内核 ABI 的 InterfaceSpec；
- 可选 GoalSpec；
- 所有真实跨模块语义变化对应的 SpecPatch（可由 Coding Agent 协助或直接维护，但必须由学生审查并与实现一致）；
- 与当前实现一致的源码、测试和构建/运行清单；若项目使用 `vos.yaml` 或其他结构化清单，应一并说明其版本和用途。

### 2.3 验证证据

提交 Lab 10 的覆盖表、不变量/故障注入矩阵、可复现的构建/测试/QEMU 串口日志、可复现归档和硬件 `pending_human_review` 记录。若使用 QEMU 板级移植，还要附上 approved QemuSpec、材料清单/哈希、QEMU commit、boot path/bypass 和邻居回归，并把它标为 `qemu_only`；不得把它当作真实板卡证据。原始协作日志不进入 Git；导出证据应遮蔽凭据并使用稳定路径别名。VOS manifest 可作为辅助，不是唯一归档格式。

### 2.5 实际耗时

记录本 Lab 实际投入小时数（一个整数），与 Lab 1–10 的耗时一起构成课程计划校准数据。

### 2.4 答辩材料

准备一张架构图、一次可重复演示和两个失败案例。每个案例说明现象、证据、根因、修复以及为何回归足以覆盖该根因。

答辩时应能现场回答：某个用户指针如何经过 ABI、页表和资源检查；一次中断如何保存/恢复进程；一次文件写入如何在崩溃后保持一致；一个模块越界变更为何需要 SpecPatch。

## 3. 自动检查与证据

本节不规定一套全局命令。使用 VOS 时可以运行 `vos doctor`、`vos spec lint`、`vos verify`、`vos report` 或 `vos submit`；使用其他工具时，提交等价的项目命令和结构化结果即可。

项目可用的自动检查由课程/项目声明，至少应覆盖构建、测试、QEMU 或硬件运行，以及报告中列出的复现命令。VOS 命令仍可作为工程化助手，但不再是 Final Lab 的强制流程：

- [ ] 所有最终 Spec 与实现、测试和构建/运行清单一致，稳定 ID 无重复或悬空引用。
- [ ] 关键构建、测试、QEMU/硬件运行都有代码/配置身份、命令、状态和产物记录。
- [ ] 必要的 public、contract、fuzz、trace 或项目等价目标均通过，失败项有完整分析。
- [ ] 报告或归档可在同一输入身份上重放；VOS manifest 如存在则与报告一致。
- [ ] 凭据、本机绝对路径和私密 flag 未出现在学生导出物中。

## 4. 人工审查

- [ ] 能解释系统最重要的三个取舍及被拒绝方案。
- [ ] 能从一个 Spec ID 追溯到实现、测试、日志和提交。
- [ ] 能说明 linked worktree 为什么不是进程或凭据安全边界。
- [ ] 能区分"本地启动""公开测试通过"和"硬件人工验收通过"。
- [ ] 能现场解释一个不变量检查器如何发现真实或注入故障。
- [ ] 能说明个性化目标的 baseline、统计方法和负面结果。
- [ ] 能指出核心逻辑、平台实现和设备信息来源的边界，并解释至少一项 HAL 可移植性取舍。
- [ ] 能说明使用的 Coding Agent、主要任务、审查过的修改和验证方式。

## 5. 长时间运行与演示

课程可以要求固定时长的 QEMU soak 或 workload，但时长、负载、资源上限和成功条件必须在提交前公布。只说"运行十分钟没有崩溃"不能证明没有泄漏；应同时采集页、对象、进程或 buffer 计数。

硬件演示由教师确认板卡、镜像身份、串口和 workload。VOS 只记录候选 evidence，不自动替代人工签字。

## 6. AI 使用边界

Lab 9 起，Codex、Claude Code、Gemini CLI、Copilot 等 Coding Agent 可以直接修改代码、测试、构建文件和 Spec。学生仍必须审查 diff、运行结果、实验边界和失败反思，并亲自完成答辩与取舍说明。不得用模型生成未发生的实验、篡改日志、伪造硬件验收或把 Fixture 当成真实运行；报告只需简要披露 Agent、主要任务、审查与验证方式。

## 7. 最终自检

- [ ] DesignSpec 的目标和 non-goals 与最终系统一致。
- [ ] 至少五个核心模块有可运行不变量检查。
- [ ] 至少一条组合不变量有跨模块证据。
- [ ] 至少两个失败案例保留了根因与回归链。
- [ ] 所有文档中的命令、路径和 Spec 类型都属于当前学生契约。
- [ ] 最终报告明确列出未完成项，不以 Fixture 或计划代替证据。
- [ ] 报告包含简要 AI 使用披露：Agent、主要任务、学生审查和验证方式。
- [ ] 最终复盘列出仍未抽象的平台假设、集中管理的硬件常量及其适用范围。
