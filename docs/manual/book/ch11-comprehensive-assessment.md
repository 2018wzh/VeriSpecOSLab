# 第 11 章：综合验收 — 从部件到整体

> **对应实验**：[Final Lab：综合验收与答辩](../labs/final-lab.md)

## 11.1 本章要解决的问题

你已经走完 10 个阶段。OS 从硬件启动一路跑到用户 Shell，能管理内存和文件、响应中断和调度进程，还配了一套独特的剖面和验证体系。现在只剩最后一个问题：**怎么证明它确实"有设计意图地运作着"，而不是侥幸"跑通了"？**

Final Lab 的重点不在做新东西。它要求你把全部工作摆出来，做一次总结、审视和辩护。本章帮你理清总结什么、怎么总结，用什么标准检验这份总结。

## 11.2 综合验收的四个维度

### 维度一：设计一致性

DesignSpec 里声明的 `required_mechanisms`，ModuleSpec 是否一一贯彻？每个 GoalSpec 有没有对应的实现和检查？`non_goals` 有没有悄悄混进实现里？

检查方法：从 `spec/design.yaml` 和 `spec/goals/` 出发，逐条追到 ModuleSpec、稳定性质、实现代码，以及 `vos.yaml` 里的 `verifies` 绑定。

### 维度二：实现正确性

你的 OS 通过了哪些测试？不变量检查器覆盖了哪些危险场景？运行时，有没有跨组件不变量持续得到验证？

检查方法：逐模块列出不变量 → 给每条不变量找到对应的检查器源码 → 确认每条都有通过的运行日志。

### 维度三：演化诚实性

你的设计在 10 个阶段里变了多少次？架构或跨模块语义变化，都补了 SpecPatch 吗？模块内的取舍，能不能从 `purpose`、`algorithm_intent` 和提交历史里找到理由？

检查方法：翻看 `spec/patches/` 和相关提交，确认每次跨模块变更都有明确理由，自动影响分析和回归更新也跟上了。

### 维度四：失败记录与反思

你遇到过哪些失败？根因是怎么定位的？学到了什么？如果重来一次，哪些选择会不一样？

检查方法：翻看 `.vos/audit`、运行 evidence 和提交历史里的失败分析，再判断这些反思够不够具体。

## 11.3 Final Lab 提交物详解

### 11.3.1 最终报告

`vos report` 从提交、Spec ID、测试、日志和 evidence 确定性生成报告，不调用模型，也不写入 Git。报告应覆盖：

1. **你的 OS 是什么（1-2 页）**：DesignSpec 里的核心目标、关键设计决策、独特剖面
2. **你的 OS 怎么运作的（3-5 页）**：一张架构图，加上每个模块的职责和数据流
3. **你怎么验证它的（2-3 页）**：不变量清单（摘要）、关键验证结果、跨组件验证
4. **它经历了什么演化（1-2 页）**：关键的设计变更（SpecPatch）和失败案例
5. **你学到了什么（500 字 Reflection）**：写具体的、可迁移的设计洞察，别停在"我学到了很多"

### 11.3.2 验证证据包

- `vos verify` 完整输出
- 每个模块至少 1 条不变量检查器通过日志
- 至少 1 条跨组件不变量的验证日志

### 11.3.3 答辩材料

- 架构图（模块 + 数据流 + 不变量标注）
- 关键设计理由与相关 SpecPatch 摘要
- 质量门禁结果一览表

## 11.4 自学者最终自检清单（扩展版）

### 设计完整性
- [ ] DesignSpec 的每项 required mechanism 和每个 GoalSpec 都能找到对应模块与检查
- [ ] 每个 non-goal 在 10 个阶段中确实没有被意外实现
- [ ] 关键设计理由能从 Spec 和提交历史追溯
- [ ] 每个实际发生的架构或跨模块语义变化都有 SpecPatch；没有这类变化时，不必硬凑数量

### 实现正确性
- [ ] 至少 5 个不变量检查器可运行且通过
- [ ] 至少 1 个跨组件不变量已在 DesignSpec 的组合不变量中定义且可验证
- [ ] 系统运行 10 分钟不崩溃、不内存泄漏
- [ ] `vos verify` 全部通过

### 文档自洽性
- [ ] DesignSpec → ModuleSpec / InterfaceSpec / GoalSpec → 实现代码 → 公开检查与 evidence，各层之间没有矛盾
- [ ] 能用一张图画出你的 OS 的完整架构（模块 + 数据流 + 不变量）

### 失败记录
- [ ] 记录了至少 2 个"曾经失败、后来修复"的案例（现象 → 定位 → 根因 → 修复 → 验证）
- [ ] 至少 1 个案例是通过不变量检查器发现的（而非功能测试）

### 如果还有时间
- [ ] 提供一个可启动的磁盘镜像（`qemu-system-riscv64 -drive file=myos.img`）
- [ ] 写一篇 500 字的 Reflection：如果重做，DesignSpec 会有什么不同？
- [ ] 录制一个 3 分钟的演示视频

## 11.5 质量门禁

| 门禁 | 要求 | 验证方式 |
|------|------|---------|
| 公开验证 | clean HEAD 上 `vos verify` 全部通过 | 自动 |
| 不变量覆盖 | ≥ 5 个不变量检查器 + ≥ 1 个跨组件不变量 | 人工审查 |
| 失败分析 | ≥ 1 个完整的失败分析案例 | 人工审查 |
| SpecPatch | 所有实际跨模块语义变化都有有效 SpecPatch | 自动影响分析 + 人工审查 |
| 最终报告 | 完整的 5 部分报告 | 人工审查 |
| Reflection | 500 字以上的反思 | 人工审查 |

## 11.6 常见陷阱

**把最终报告写成日志。**"第 1 周我做了 X，第 2 周我做了 Y……"这是流水账，不是报告。报告写给不了解你过程的人，讲清楚设计是什么、为什么这样做、怎么验证的。

**验证证据不足。**"系统能跑 Shell"是个 demo，不算验证。你要拿出不变量检查器的通过日志、测试套件的通过输出、跨组件不变量的验证结果。

**失败分析太浅。**"内存分配器崩溃了，我改了 freelist 的指针，好了。"这不叫分析。分析得回答：崩溃时具体是什么状态？违反了哪个不变量？根因出在哪？为什么之前的检查器没发现？

**Reflection 太空。**"通过这门课我学会了操作系统。"这不叫反思。好的反思是具体的："我在阶段 3 选了 buddy system，到阶段 5 才发现它让连续物理页分配变得困难。如果重来，我会在阶段 3 就把阶段 5 的需求考虑进去。"

**没有架构图。**"我的 OS 太简单，不需要画图。"再小的教学 OS 也有模块交互。一张好的架构图，能帮你自己看清模块间的依赖关系，也让审查者一眼明白你的设计。
