# 附录：CTF 与 flag

本附录服务于 Lab 1 的双环境热身，解释任务形式、验证边界和隐私要求。

## 什么是 CTF 与 flag

CTF（Capture The Flag）是一类以明确目标驱动实践的安全竞赛。参赛者通过分析系统、协议或二进制，找到一段特定格式的字符串，即 flag。课程借用这种形式，不把 Lab 1 变成漏洞利用题。

Lab 1 的 flag 位于教师下发的文件系统镜像中。学生必须沿着真实读取路径获得内容：

```text
镜像/块设备 → 超级块 → inode → 目录项 → 文件数据 → 输出
```

## 为什么适合作为热身

- 目标确定，程序输出可以自动核对；
- 同一数据可以分别经过 Linux 文件接口和裸机读取路径，便于比较抽象层；
- 读取失败可以定位到块设备、文件系统或输出链路，而不只得到“程序没跑”的模糊结果；
- 学生会在进入完整内核前接触链接、镜像格式、设备访问和串口证据。

## 验证边界

正确输出只能证明本次运行获得了目标内容，不能单独证明实现没有硬编码。验收还要检查：

1. 源码和构建产物中不存在明文预期 flag；
2. 每名学生或每次发放使用不同内容，避免共享固定答案；
3. 日志能绑定镜像哈希、构建身份和运行环境；
4. 至少对块读取、目录查找和文件读取保留可诊断信息；
5. 失败时返回非零状态或明确错误，不把空字符串当作通过。

## 隐私与提交

真实 flag 可能是学生唯一凭据，不应进入 Git、公开报告或截图。公开证据应显示格式、长度和稳定哈希，或使用遮蔽形式，例如 `flag{ab…yz}`。教师侧可以在受控环境中保存完整期望值并完成比对。

Agent 对话同样不能包含完整 flag。需要诊断解析结果时，提供块号、inode、长度、内容哈希和受限十六进制片段即可。

## 与后续 Lab 的关系

Lab 1 的轮询交替输出不是调度器，文件系统读取框架也不是完整内核。它只建立后续实验需要的直觉：

- Lab 2 建立正式启动链和串口契约；
- Lab 3 管理内存与地址空间；
- Lab 4 引入中断驱动设备；
- Lab 5 才建立用户态、进程和系统调用；
- Lab 6 完成可写文件系统与崩溃一致性。
