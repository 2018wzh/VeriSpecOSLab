建议成片：7 分 45 秒至 7 分 55 秒

P1　VeriSpecOSLab（0:00–0:15）

各位老师好，我是华东师范大学 Glenda 队的汪子昊。今天介绍 VeriSpecOSLab，一套规格驱动的个性化 OS 设计与 Agent Coding 实验平台。我们的目标，是让学生真正设计自己的操作系统。

P2　代码能通过，不等于学生完成了设计（0:15–0:40）

xv6、rCore 等实验很适合讲清操作系统机制。不过这类实验通常已经给定内核与架构，学生补全指定代码，教师根据实现和测试评分。代码补全恰好是 Coding Agent 最擅长的工作。学生如果只把任务交给 Agent，既可能跳过设计，也未必有能力维护生成的代码。即使系统最终运行起来，我们仍然不知道架构是谁决定的、取舍是否经过思考。

P3　教学目标发生两次转向（0:40–1:05）

因此，我们让学生从零开始，逐步实现具有个人设计的操作系统。他们仍要掌握代码实现，同时还要定义目标、划分模块和接口、解释取舍，并学会约束和复核 Agent。教师则从代码审阅转向评审设计、演化过程和证据。正确性仍然是门槛，但不再是唯一的评价对象。

P4　一个可执行的教学闭环（1:05–1:30）

围绕这个目标，我们建立了一条教学闭环。学生理解 Lab 问题，把方案写入 Spec；Agent 按照已提交的 Spec 实现；VOS 检查修改范围，再交给真实 Runner 验证；教师依据设计、提交和证据提出意见。无论成功还是失败，每次尝试都会留下时间线。

P5　Spec 把学生的设计变成可检查输入（1:30–2:00）

学生先用 DesignSpec 写下整体方向，再通过 ModuleSpec、InterfaceSpec、GoalSpec 和 SpecPatch 落实模块、接口、个人目标与跨模块修改。`owns` 限定 Agent 的修改范围，properties 和 checks 进入验证。规格按 L1 到 L3 逐步加深，不要求学生第一周就写出完整架构，也不预设唯一答案。

P6　模型提交结果，平台决定是否通过（2:00–2:30）

Spec 提交后，VOS 创建隔离的 Git worktree，把任务和修改范围交给 Agent。Agent 必须返回结构化结果，平台再读取真实 diff，运行构建、公开测试、契约测试、固定种子 fuzz 和有界 trace。模型声称完成不会改变状态。越界修改、测试失败或原项目漂移都会被拒绝，全部检查通过后才形成提交。

P7　核心链演示（2:30–3:00）

[指向四段流程图。]

这里展示的是一条真实的核心链。学生手写 Spec，Agent 在隔离工作区实现，Runner 执行已有测试以及由 obligation 生成的行为样例，report 再绑定提交、规格和日志。到了硬件阶段，QEMU 与实体板证据分开记录。我们关心的不只是命令有没有成功，还要知道谁对决定负责、结论由什么证据支持。

P8　让 AI 回答回到可核对来源（3:00–3:25）

[进入页面后单击视频。]

这些功能来自我们在操作系统课程和内核开发中的实际困难。学生缺少背景知识时，裸模型很容易把不可靠的解释说得十分确定。我们把课程材料、标准和板卡手册放进知识库，让 ask 和 review 用 citation 指回原文。画面是一条真实通过结构化校验的记录。citation 让回答有迹可循，但最后仍由学生判断。

P9　运行时写页故障（3:25–3:55）

[进入页面立即单击视频。视频 0–6 秒对应 TCG，6–12 秒对应 GDB 与插桩，12–18 秒对应可视化。]

调试是另一个真实痛点。内核切换到用户态后，用户页第一次写入时的权限错误可能变成 trap 风暴，串口上却只有重复输出。我们为此实现了只读 QEMU TCG 插件。Debug Agent 先找到异常跳转，再用 GDB 确认 `scause` 为 15、故障地址和 PC，定位到页表映射遗漏 `PTE_W`。证据仍不足时，它才在 detached worktree 中加入最小插桩，并生成因果视图。案例由 v2 schema 测试覆盖，TCG trap 和 MMIO 通道另有原生 QEMU 验收；诊断不能冒充修复通过。

P10　Agent 生成测试，Runner 裁决结果（3:55–4:20）

内核开发也不能只依赖几条已有样例。现有测试没有覆盖某条 Spec obligation 时，`vos verify` 会让 Agent 生成不同类型的 TestPlan，再产生一次性的测试补丁、suite 和 oracle。补丁只进入临时工作区，不能修改 Spec 或运行档案。Runner 随后真实执行命令，检查退出码、超时和输出规则，并保存完整结果。Agent 负责补充测试，是否通过仍由 Runner 决定。

P11　自动生成 QEMU 板级模型（4:20–4:50）

[进入页面立即单击视频。]

物理板卡移植往往需要反复烧写、重启和看串口，学生很容易把大量时间耗在环境上。我们的做法是为目标板生成 QEMU 板级模型，把它作为仿真与实体板验证之间的缓冲层。VOS 根据学生提供的材料生成 candidate，学生审查并提交后，Agent 才在隔离工作区执行。画面先展示 H5 的七项 QEMU trace，再切到 Orange Pi Prime 四核串口。QEMU 可以提前暴露问题，但真实时钟、引脚和外设仍须由实体板验证。

P12　用 commit 精确记录并复原（4:50–5:15）

[进入页面立即单击视频。]

最后一个痛点是实验结果难以复现。我们把每次修改和运行绑定到明确的 Git commit、Run ID、Spec 和验证报告。教师可以从 Portal 找到权威运行，在 detached worktree 中恢复对应 commit，再次执行验证。commit 负责复原代码状态，报告和脱敏归档负责还原当时的执行证据，两者共同组成完整记录。

P13　指导书先提供设计所需的背景（5:15–5:35）

我们还重写了实验指导书。Book 加入更多操作系统历史，帮助学生理解今天的资源模型和内核设计为什么会变成现在这样；Lab 则给出任务、预期现象和自检点。为了降低起步门槛，Lab 1 设置了 CTF 式热身，让学生先熟悉编程和板卡环境，再开始设计内核。

P14　两个内核、两种架构（5:35–6:10）

我们用两个真实内核验证整套课程。xv6 加 VisionFive 2 启动四个 U74 hart，经 SPI U-Boot、TFTP 和 SD 文件系统运行完整 usertests，得到 `ALL TESTS PASSED`。我们在课程中开发的 Glenda 加 Orange Pi Prime，则先完成 H5 的七项 QEMU trace，再由实体板确认四核、GICv2、定时器、MMC 和 EL0 工作负载。两套项目都在 Portal 中闭合，但证据仍分层记录。

P15　试讲反馈怎样改变课程入口（6:10–6:40）

2026 年暑期，我们面向华东师范大学 2025 级计算机拔尖班的 15 名学生进行了两节试讲。课堂暴露了不少实际问题：初版 Spec 太复杂，学生缺少背景知识，大型工程的工具门槛也偏高。我们没有把这次试讲包装成效果统计，而是根据这些反馈修改产品，简化 Spec，补充历史和设计比较，并加入 CTF 热身、统一 CLI 和 doctor。

P16　借鉴、增量贡献与 AI 使用（6:40–7:00）

项目的直接灵感来自上海交通大学团队的 SYSSPEC 工作，我们把规格驱动的方法用于完整 OS 课程，并以 MIT xv6 和 Glenda 为案例。本队实现了 v2 Spec、受控 Agent、Runner 与证据体系、课程材料、Portal、板卡移植和跨架构验证。研发使用 Codex、DeepSeek V4 Pro 和 ChatECNU ecnu-plus；AI 生成内容都经人工修改和真实验证。

P17　下一学年与 Glenda-Chimera（7:00–7:25）

这套方案将在 2026 年秋季正式用于 2025 级拔尖班。我也会以助教和开发者的身份和学生一起使用它，并把 Glenda-Chimera 作为自己的验证目标。我们计划用 Rust 编写 seL4 风格微内核，用 Go 开发 RPC 风格的系统服务，再通过稳定的 IPC 边界，让服务代码可以在内核态和用户态之间切换。它目前是下一阶段目标，不是已经完成的成果。

P18　重新定义 OS 实验的评价对象（7:25–7:50）

这就是我们希望完成的转变。学生从零开始设计自己的操作系统，用 Spec 约束 Agent，再用真实验证检查实现；教师则依据设计、演化过程和证据进行评价。我们没有减少学生思考，而是把学生的思考从重复编码提升到系统设计，同时训练他们在真实工程中使用 Agent 的能力。谢谢各位老师。
