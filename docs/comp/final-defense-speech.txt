建议成片：7 分 45 秒至 7 分 55 秒

P1　VeriSpecOSLab（0:00–0:15）

各位老师好，我是华东师范大学 Glenda 队的汪子昊。今天介绍 VeriSpecOSLab，一套规格驱动的个性化 OS 设计与 Agent Coding 实验平台。我们的目标，是让学生真正设计自己的操作系统。

P2　代码能通过，不等于学生完成了设计（0:15–0:40）

xv6、rCore 等实验很适合讲清操作系统机制。不过在常见流程里，架构已经给定，学生补全代码，教师根据实现和测试评分。代码补全恰好是 Coding Agent 最擅长的工作。学生即使交出能运行的代码，我们仍然很难判断：架构是谁决定的，取舍是否经过思考，测试通过又是否只来自 Agent 的自我声明。

P3　教学目标发生两次转向（0:40–1:05）

因此，我们把教学目标向前推进了一步。学生仍要掌握代码实现，同时还要定义系统目标、划分模块和接口、解释取舍，并学会约束和复核 Agent。教师则依据设计、演化过程和证据评价学生。正确性仍然是门槛，但不再是唯一的评价对象。

P4　一个可执行的教学闭环（1:05–1:30）

围绕这个目标，我们建立了一条教学闭环。学生理解 Lab 问题，把方案写入 Spec；Agent 按照已提交的 Spec 实现；VOS 检查修改范围，再交给真实 Runner 验证；教师依据设计、提交和证据提出意见。无论成功还是失败，每次尝试都会留下可复查的时间线。

P5　Spec 把学生的设计变成可检查输入（1:30–2:00）

学生使用五类 Spec 表达设计。DesignSpec 记录系统方向，ModuleSpec 说明模块职责、性质和错误，InterfaceSpec 固定跨模块语义，GoalSpec 描述可度量的个性化目标，SpecPatch 解释必要的跨模块修改。其中，`owns` 限定 Agent 可以修改的范围，properties 和 checks 进入后续验证。规格按 L1 到 L3 随课程逐步加深，不要求学生一开始就写出完整架构，也不会替学生预设唯一答案。

P6　模型提交结果，平台决定是否通过（2:00–2:30）

Spec 提交以后，VOS 会创建隔离的 Git worktree，把任务和可修改范围交给 Agent。Agent 必须返回机器可检查的结构化结果，平台再读取真实 diff，运行构建、公开测试、契约测试、固定种子 fuzz 和有界 trace。模型说自己完成了，并不会改变任务状态。越界修改、测试失败或者原项目发生漂移，都会被明确拒绝。只有全部检查通过，结果才会形成独立提交。

P7　核心链演示（2:30–3:00）

[指向四段流程图。]

这里是完整的核心链。设计由学生写入 Spec，实现发生在隔离工作区；验证既执行已有测试，也可以把未覆盖的 obligation 转成行为样例，但结果始终由 Runner 裁决；report 再绑定提交、规格和日志。到了硬件阶段，QEMU 与实体板证据分开记录。每一步都要回答：谁对决定负责，结论由什么证据支持。

P8　让 AI 回答回到可核对来源（3:00–3:25）

[进入页面后单击视频。]

学生缺少背景知识时，裸模型很容易把不可靠的解释说得十分确定。VOS 的 ask 和 review 从课程知识库取材，并用 citation 指回教材、代码或固定版本资料。画面是一条真实通过结构化校验的记录。citation 只说明回答根据什么，不保证答案天然正确，最后仍由学生判断。

P9　运行时写页故障（3:25–3:55）

[进入页面立即单击视频。视频 0–6 秒对应 TCG，6–12 秒对应 GDB 与插桩，12–18 秒对应可视化。]

更棘手的是只表现为黑屏、超时或 trap 风暴的运行时故障。这个案例中，用户页第一次写入后不断陷入内核。Debug Agent 先用只读 TCG 找到异常跳转，再用类型化 GDB 确认 `scause` 为 15、故障地址和 PC，由两条 observation 定位到页表映射遗漏 `PTE_W`。证据不足时，它才在 detached worktree 中加入最小插桩，并把观测、假设和因果关系组织成可交互视图。案例由 v2 schema 测试覆盖，TCG trap 和 MMIO 通道另有真实原生 QEMU 验收；诊断不能冒充修复通过。

P10　Agent 生成测试，Runner 裁决结果（3:55–4:20）

现有测试没有覆盖某条 Spec obligation 时，`vos verify` 可以让 Agent 生成 TestPlan，再产生一次性的测试补丁、suite 和 oracle。补丁只能进入临时工作区，不能修改 Spec、Git 元数据或运行档案。Runner 随后真实执行命令，同时检查退出码、超时和输出规则，并保存 plan、patch、标准输出和结果文件。Agent 帮助扩展测试空间，但它没有宣布实现正确的权力。

P11　自动生成 QEMU 板级模型（4:20–4:50）

[进入页面立即单击视频。]

板卡移植常常同时涉及启动链、设备模型和固件边界。VOS 先盘点学生提供的材料，生成 QEMU candidate；学生审查并提交后，Agent 才在隔离工作区执行。画面先展示 H5 的七项 QEMU trace，再切到 Orange Pi Prime 四核串口。QEMU 只形成 `qemu_only` 结论，真实时钟、引脚和外设仍须由实体板验证。

P12　用 commit 精确记录并复原（4:50–5:15）

[进入页面立即单击视频。]

为了让实验过程可以复查，每次实现都会落到独立 commit，并与 Run ID、Spec 和验证报告绑定。教师可以从 Portal 找到权威运行，再在 detached worktree 中回到对应 commit，重新执行验证。原始日志并不塞进 Git，而是保存在匹配的脱敏归档中。因此，commit 负责复原代码状态，报告和归档负责还原当时的执行证据，两者不能混为一谈。

P13　指导书先提供设计所需的背景（5:15–5:35）

我们还重写了实验指导书。Book 介绍操作系统历史、宏内核与微内核的争论、资源模型和硬件边界；Lab 给出任务、预期现象和自检点。Lab 1 加入 CTF 式热身，帮助学生熟悉环境。教材提供背景和抓手，但不替学生决定架构。

P14　两个内核、两种架构（5:35–6:10）

我们用两个案例检验了这套方法。xv6 在 VisionFive 2 上启动四个 U74 hart，经 SPI U-Boot、TFTP 和 SD 文件系统运行完整 usertests，最终得到 `ALL TESTS PASSED`。Glenda 则把同一流程迁移到 AArch64 和 H5。七项 QEMU trace 验证软件与设备语义，Orange Pi Prime 串口再独立确认四核、GICv2、定时器、MMC 和 EL0 工作负载。两个案例都在 Portal 中闭合课程流程，但 QEMU、connected、实体板和教师复核仍然分层记录。

P15　试讲反馈怎样改变课程入口（6:10–6:40）

正式教学前，我们面向华东师范大学 2025 级计算机拔尖班的 15 名学生进行了两节暑期试讲。这不是统计意义上的效果实验，但暴露了三个具体问题：初版 Spec 负担过重，学生缺少背景，大型工程的工具门槛偏高。我们据此把规格收敛为五类并分散到各个 Lab，补充历史和设计比较，同时加入 CTF 热身、统一 CLI 和 doctor。

P16　借鉴、增量贡献与 AI 使用（6:40–7:00）

项目借鉴了 SYSSPEC 和 SPECFS 的规格驱动思想，并使用 MIT xv6 与 Glenda 作为案例。本队完成的增量包括 v2 Spec、教学流程、受控 Agent、Runner 与证据体系、课程材料、Portal、VisionFive 2 移植和跨架构案例。研发中使用了 Codex、DeepSeek V4 Pro 和 ChatECNU ecnu-plus；生成内容都经过人工修改，并由结构化验收、构建、QEMU 或实体板结果核实。相关来源和许可证在附录中完整列出。

P17　下一学年与 Glenda-Chimera（7:00–7:25）

这套方案将在 2026 至 2027 学年进入正式教学。我也会以助教和学生开发者的身份，使用它实现并验证 Glenda-Chimera。我们的目标是用 Rust 编写 seL4 风格微内核，用 Go 开发 RPC 风格的系统服务，并通过稳定的 IPC 边界，让服务代码可以在内核态和用户态之间切换。它目前是下一阶段的验证目标，不是已经完成的成果。

P18　重新定义 OS 实验的评价对象（7:25–7:50）

VeriSpecOSLab 改变的是 OS 实验的评价对象。代码和测试说明系统能否运行，Spec、提交和证据则说明学生为什么这样设计，又怎样确认 Agent 的实现可信。教师也能把精力放回设计评审。我们没有减少学生思考，而是把思考从重复编码提升到系统设计。谢谢各位老师。
